# 販促の取り込みプレイブック（どのパターンでも即・台帳化）

原則は変わらない：**人は台帳を書くだけ／数値は自動で集計**。
どんな販促（PDF・施策の連絡）が来ても、この手順で「schedule → creatives → 効果データ」に落とすと、
店舗詳細・施策の効果・**年間販促（振り返り）**に自動で並ぶ。

## 0. 届いたらまず特定する4点
1. **店舗**（コード。`config/stores.yaml` で名前→コード）
2. **種類（kind）**（下の表）
3. **期間**（開始・終了。単日なら開始のみ）
4. **PDFの有無**（POP/チラシ/メニュー/グランドメニュー）

## 1. 施策を台帳に足す（必須・全パターン共通）
`config/schedule.yaml` の `campaigns:` に1行：

```yaml
- { id: r<店コード>-<slug>, stores: ["<店コード>"], title: <表示名>, kind: <種類>,
    start: "YYYY-MM-DD", end: "YYYY-MM-DD", note: "<一言メモ>" }
```

- `id` は一意（例 `r1151-lunch`）。`stores` は複数可、全店は `scope_all: true`。
- 単日イベント（GM改定・ランチ変更・打ち出し日）は `end` 省略可。
- `target:`（目標売上・円）を書けば達成率が出る（アプリ内でも入力可）。
- `bucket:`（任意）＝この施策が効くFW ABC部門（`コース`/`食べ放題`/`ランチ`/`アラカルト`/`飲み放題`）。
  書くと施策詳細に **その部門の実績＋構成比** が出る（宴会=`コース`、食べ放題=`食べ放題`）。
  省略時は種類から自動推定（`lunch`→ランチ・`bounenkai`→コース）。
- `items:`（任意）＝商品名キーワードの配列（部分一致）。書くと施策詳細に **該当商品の実績＋
  部門内構成比** を「表示」で開く**商品内訳**として出す（クリスマスコース・忘新年会コース・
  ケーキ/ジェラート/パフェ等を名指し）。例 `items: ["ジェラート"]` / `["クリスマス"]`。
  ※実数は **FW ABCの最新1ヶ月**。**月ごとに並べる（1ヵ月毎）には月次ABC蓄積が別途必要**。

## 2. PDFがあれば制作物に足す（POP/チラシ/メニュー）
1. PDFを `assets/creatives-src/<ファイル名>.pdf` に置く。
2. `config/creatives.yaml` に1行：

```yaml
- id: <一意id>
  title: <表示名>
  campaign: <上の施策id>      # これで対象店・種類を継承
  date: "YYYY-MM-DD"
  file: creatives/<年>/<施策id>/<ファイル名>.pdf   # R2キー。basename が assets と一致すればデプロイ時に自動アップ
```

## 3. 効果データを拾う（種類別・下の表の「効果ソース」）
数値は基本は月次で自動集計（前年比・前月比・集客）。
それだけで足りないパターンは、FWツールで引いて対応する JSON台帳に貼る。

| 種類(kind) | 例 | schedule | PDF | 効果ソース（貼り先） | 使うFWツール |
|---|---|---|---|---|---|
| `gm` GM改定 | メニュー改定 | 開始日 | グランドメニュー | 月次自動（前年比/前月比・集客） | ―（自動） |
| `osusume` おすすめ/フェア | 秋おすすめ | 開始〜終了 | チラシ/POP | 月次自動＋(必要なら商品) `products` | `abc-store-probe` |
| `lunch` ランチ変更 | 日替わり/沼パスタ | 開始日 | ランチメニュー | `config/lunch_analysis.json`（店別・食数/原価/構成比/トッピング） | `lunch-analyze`／`abc-store-probe` |
| `bounenkai` 忘年会 | コース | 開始〜終了 | コースメニュー | 月次自動（客数・売上） | ―（自動） |
| `dev` その他開発/環境・オペ | 電子タバコ可・空調改善・新機材 | 開始日 | （任意） | `config/env_effects.json`（時間帯 前後・深夜の品数×単価） | `hourly-store-probe`／`abc-totals-probe`／`menu-hourly-probe` |
| `closure` 休業 | 改装休業 | 開始〜終了 | ― | ―（在不在の把握のみ） | ― |

### 効果データ台帳の形（貼り先）
- **月次（自動）**: 何もしない。確定月が出れば施策詳細に 実績＋前年比＋前月比＋集客 が乗る。
- **`config/lunch_analysis.json`**: `stores[]`（store_code/menu_title/period/lunch{sales,cost_rate}/daily_meals/toppings/menu）。→ 店舗詳細「新ランチ効果」＋一覧。
- **`config/env_effects.json`**: `effects[]`（campaign_ids/base_label/after_label/periods[]{covers,sales,items,food_*,drink_*,nomihoudai,night_*}）。→ 施策詳細「効果（時間帯別・前後）」＋深夜分解。
- **`products`（ABC）**: 全店売れ筋は自動取込。個店の商品は `abc-store-probe` で確認。

## 4. 反映（毎回同じ）
1. `node --check web/app.js`（画面を触ったら）
2. `bash scripts/check.sh`（Python/取込を触ったら）
3. commit → push（main）
4. デプロイ：`deploy.yml` を実行（creatives-sync でPDFをR2へ→export→Cloudflare公開）

## 5. 年間で振り返る
- TOP「年間販促 →」で年（2024〜今年）を選ぶと、四半期別に施策が並ぶ（実績＋直近差異）。
- 各行「詳細を確認 →」で施策詳細（前後・深夜分解・POP・要因メモ）へ。
- 過去分（2024〜）を振り返りたいときは、その施策を上の手順で `schedule.yaml` に足す（効果データは分かる範囲で）。

## 店舗別ABC（売れ筋＋部門）の収集
- `abc-store-ingest`（fw.yml, `--abc-store <店コードor店名>` `--month YYYY-MM`）で1店ずつ、
  商品ABC上位40品＋部門内訳（コース/ランチ/アラカルト/飲み放題/食べ放題）をNeonに焼く。
  `source=fw_abc_<コード>` で店ごとに冪等キーを分けるので、並行実行しても互いに上書きしない
  （FWは同時ログインに耐える＝全店を並行で流せる）。部門が切替らない店は分類=グループへ
  自動フォールバック。取り込むと店舗詳細「部門構成」「売れ筋商品」と横断ビューに出る。
- `abc-coverage`（fw.yml, FWログイン不要）で全稼働店の 商品数・部門数・バケット別売上を
  1回のDB照会で一覧し、未取得の店を洗い出す。

### 月次ABC（1ヵ月毎に並べる）
- 冪等キーは (source, grain, date)。`abc-store-ingest` は date=対象月の月初で焼くので、
  **月をまたいで取り込めば月ごとに共存＝蓄積される**（上書きされない）。export はこれを
  `departments_monthly[店][月]` / `products_monthly[店][月]` に月次シリーズ化し、施策詳細で
  部門・商品を **1ヵ月毎＋前年同月比** で並べる（`bucket`/`items` 指定時）。横断の
  「忘新年会・宴会まとめ」も宴会=コース部門の全店 売上・構成比・前年比を出す。
- **FW ABC は過去月も引ける**（`--month 2025-12` のように任意の月を渡せる）。したがって
  前年比は蓄積を待たずに**遡って埋められる**。`abc-ingest`（全店）はグループ売れ筋(_group)
  のみで、店別の月次には使えない（店別は `abc-store-ingest`）。
  - ⚠ **画面の操作順が決まっている。日付範囲を入れてから店舗を選ぶこと。**
    逆にすると、店によってはグリッドが全月0品で返る（1137 と 1728 以降の新しい店で確認。
    同じ店・同じ月でも `abc-store-probe`（日付→店舗選択の順）なら普通に取れる）。
    17店では順序が逆でも取れていたため、長らく「FWに過去月のABCが無い店がある」と
    誤解していた。この誤解は2度ぶん残っている: 2026-08-27 に 1739 で「FWは過去月の
    商品明細を返さない」と結論づけ、2026-09-02 にそれを「誤り」と訂正したが、
    どちらも的を外していて、実際は順序ひとつだった。
    **「FWにデータが無い」と結論づける前に、probe と同じ手順で1回引いて確かめること。**
  - 空月の判定を「グリッドの待ち時間」で決めてはいけない。待ちを短くすると
    データのある月を空と読み、しかもその判定が後続の月にも効いて全月が空になる
    （1743 で24ヶ月すべてこれで空と記録した）。空かどうかは常に同じ粘り方で決める。
  - 月は**新しい順**に回す。データのある月に先に当たるので、そのあと空月が3ヶ月
    続いたら開店前と判断して打ち切れる（新店で開店前の空月に時間を使わない）。
  - 書き込みは**月ごと**。冪等キーが source×grain×date で source は店ごとに分かれて
    いるため、1ヶ月だけ差し替えても他へ触らない。途中で落ちてもそこまでの月は残る。
  - 検算のやり方: 引いた月の `dept_sales` 合計を、同じ店・同じ月の `sales`（月別日別売上推移）
    と突き合わせる。**両方とも税込なので 99〜100% になるのが正常**（実測: 1006 の
    2025-04〜2025-08 は 99.8%）。以前ここに「95〜97%程度なら妥当」と書いていたが、
    これは税込と税抜が混ざった状態で測った数字で、誤り。90%を切る/105%を超える月は
    部門の取り漏れか、売上側の出どころ違いを疑うこと。
    既定月がそのまま返っていると、別の月を引いても同じ値になるので一発で分かる。
    `query.yml` の指標に `dept_sales`/`product_sales` があるのはこの検算のため。
- 自動化: `abc-monthly.yml`（毎月6日 05:20 JST）が稼働店を `config/stores.yaml` から動的に
  matrix 化し、前月ABCを1店ずつ（4並行）取り込む。手動は workflow_dispatch。
  取込後は `deploy.yml` で画面へ反映（毎日のデプロイでも拾う）。
- 遡り取り込み: `month` は複数・範囲で渡せる（`2025-11,2025-12` / `2024-09..2026-07`）。
  1店1ログインで月を回すので、24ヶ月でもログインは1回。データのある月は1ヶ月あたり
  10秒ほど、空月は待ち切るぶん80秒ほどかかる。`budget_minutes`（既定70分）を超えたら
  残りの月を告げて打ち切り、そのまま流し直せるコマンドを印字する。
  取り込み後は必ず `query.yml` の `dept_sales` を `group_by=date` で見て、月ごとに
  値が変わっていること・同月の `sales` と 99〜100% で整合することを確かめる。
  ログに `⚠ 部門合計が他の月と一致` が出たら、日付が効かず同じグリッドを読んだ疑い。

### 月次売上のバックフィル（月別日別売上推移）
- 画面は1店ずつ「対象月を末尾とする12ヶ月」を出し、**前年実績・客数前年実績**の列も持つ。
  つまり1回の照会で約24ヶ月ぶんが書ける。対象月 `2025-08` なら
  グリッド 2024-09〜2025-08 ＋ 前年列 2023-09〜2024-08。
- `uriage-backfill.yml`（手動）で `months=2025-08,2024-08` のように**対象月をカンマ区切り**で
  渡すと、稼働店を matrix 化して1店ずつ（4並行）遡る。1店だけ試すときは `store` に
  店コード or 店名の一部。CLI は `fw-daily --mode monthly --month <月,月> --abc-store <店>`。
- 反映の判定は「**グリッドの最新月＝対象月**」。対象年の行があるかで見ると、既定の直近12ヶ月にも
  その年の行が混ざるため（例: 対象月2025-08 と既定グリッドの2025-10〜12）、動いていないのに
  成功と誤判定する。`検 索` は同じ字面のボタンが複数あり得るので候補を順に押し、
  実際にグリッドが動いたものだけを採る。2店続けて反映できない対象月は以降とばす。
- `replace_actuals(..., scope_stores=True)` で消す範囲に店を含めるため、**1店だけ流しても
  同じ source・同じ月の他店の実績は消えない**（matrix で並行に回せる理由）。
- `fw-daily --mode monthly-coverage`（fw.yml, FWログイン不要）で店×月の欠けを一覧できる。
  `--abc-from`/`--abc-to` に YYYY-MM を渡す。バックフィルの前後で回して穴を確かめる。

### FW以外のPOS（uレジ / ダイニー）
- FWに連動していない店は、FWをどれだけ掘っても実績が出てこない。`config/stores.yaml` の
  `pos:` に出どころを書く（既定 `fw`／`uleji`＝uレジ管理／`dainy`＝ダイニー管理アプリ）。
  `monthly-coverage` はこの店を「✗ データ無し」ではなく「― FW未連動」として分けて出すので、
  取り漏れの調査に時間を使わずに済む。
- 現状 `pos: uleji` は **1766 ぎふや 福岡天神店**（FW連動が未実施）。月次売上・客数は
  uレジ管理から入れる必要がある。取込口はまだ無い（管理サイトの構造を確認してから作る）。
- FWで取りきれない粒度は、ダイニー管理アプリ／uレジ管理側なら出せることがある。
  ただし「FWの制約」と決める前に、上の検算で本当に取れないのかを確かめること。
  過去月ABCが取れない店があると2度結論づけたが、2度とも間違いで、実際は画面の
  操作順（日付→店舗選択）だった。手作業のエクスポートを頼む前に、まず自分の手順を疑う。

### 施策と部門/商品の紐づけ（bucket / items）
- `bucket:` は 標準バケット（コース/ランチ/アラカルト/飲み放題/食べ放題）だけでなく、
  **FWの生部門名の部分一致**でも解決する（`resolveDept`）。例: ルクアLargoの
  `パフェ`/`ケーキ`/`テイクアウトジェラート` は独立部門なので `bucket: パフェ` 等で
  その部門の 売上・構成比・前年比 を月次表示できる（標準バケットのアラカルトに丸めない）。
- `items:` は商品名キーワード（部分一致）。施策詳細の「表示」で 月×商品（部門内構成比・前年比）
  を展開する。季節限定（例: ルクアの“パフェスノー”＝夏限定おすすめ）は非シーズンにABC計上が
  無いので、月次の商品内訳で自然に空欄になり季節性が分かる。
- 部門が取れない店: FWのABCで『部門』を選んでも全商品グリッドのままになる店がある
  （＝商品が部門に紐づいていない）。ラジオは押せている（click=True）のにグリッドが
  変わらないので、コードでは回収できない。`abc-store-probe --abc-levels 部門` の
  末尾の判定まとめで一発で分かる。
  - 全期間だめ: **1069 ひよこ飯店 / 1137 たいだい**。テキスト/role=radio/Bootstrapラベル/
    生DOMの4方式すべてで確認済み。`config/stores.yaml` に `abc_dept: false` を入れてあり、
    取込は部門を試さず飛ばす（毎月の空振りを止めるため）。
  - **古い月だけだめ: 1111 ちゃーちゃん / 1151 NagaGutsu / 1168 GOLD京都ポルタ**。
    2026-07 以降は部門が取れており、2025-12 をprobeで引くと0件（3店とも部門・グループの
    両方で0件。ラジオは押せていて click=True、視覚行は 1111=320 / 1168=268 出ている。
    つまり「切替に失敗した」のではなく「部門が無い」）。POSのマスタが途中で
    切り替わったと見るのが自然。
    **`abc_dept: false` にしてはいけない**（これから先は取れるので、飛ばすと今後の
    部門が入らなくなる）。過去月の部門の穴は埋まらないものとして扱う。
  - 1766 ぎふや福岡天神は FW未連動（`pos: uleji`）。ABCの対象からも外してある。

## 店長会資料DL（損益管理→実績管理業務）— 調査結論: 取込対象外
- 実体は 出力ボタン→ `POST .../ProfitLoss/ManagerMeetingDocumentExcel/`。multipart で
  DB接続情報＋全社の店コード＋期間を送ると旧Excel(.xls, 約4MB)が**レスポンス本文**で返る
  （download/response イベントは出ないので `manager-dl` モードは page.request で同期再送して取得）。
- 中身は**1店1シート**（FW全社＝当社の稼働店以外も多数）の**店長会用レポート雛形**。
  各シートに 売上/ＦＬ合計/利益/集客/客単価・前年実績/予算/実績/予算達成率/前年比較 の
  “ラベル”はあるが**値セルは空**（「青いセルは自動計算」＝Excelで開いた時に式で埋まる）。
  → **DBに焼ける実数値は無い**。`fw-budget --mode manager-dl` は「雛形である」ことを
  非ゼロ数値セル数で確認する診断として残す（取込はしない）。
- 欲しいKPIの供給元（既存ツールで充足）:
  原価率＝ABC部門グリッド（`export.py` の bucket.cost_rate）／利益＝売上−原価／
  売上・客数・客単価＝monthly・hourly／予算（達成率の分母）＝fw-budget。

## 目標とメモはどこに置くか（2026-09 に決めた）

- **台帳（config/schedule.yaml）** … 施策の定義。いつ・どこで・何を・どう測るか。
  git 履歴がそのまま販促履歴になる。
- **アプリ（画面 → /api/targets・/api/notes → Neon）** … 目標と振り返りメモ。
  期中に何度も直すもの。店長が git を触らずに直せる必要がある。

目標は以前この両方に書けたが、書き手がどちらに入れるか迷い、どちらが効いて
いるのかも分からなかった。台帳の `target:` は読まなくなった（`schedule-lint` が
エラーにする）。

**鍵は `id@開始年`**（例 `r1006-osusume@2026`）。目標とメモは施策の「回」に
ぶら下がる。id だけで持っていると、来年の秋おすすめが今年の目標・メモを
上書きしてしまう。台帳の id を年込みに改名する必要はない（開始日から自動で付く）。

素の id で入っている古い行は画面から読めるようにしてある（移行の橋渡し）。
DBを揃えるときは一度だけ:

    python -m hansoku.cli promo-migrate-keys --dry-run   # 移す対象を確認
    python -m hansoku.cli promo-migrate-keys             # 実行

すでに新しい鍵で入っている行は触らない（画面から入れ直したぶんを古い値で
潰さない）。台帳に無い id の行も触らない。何度流しても同じ。

## 比率は「1つの表の中」で割る（2026-09 に外部監査で発覚）

税込に統一したとき、**分母だけを動かして分子を見直さなかった**ため、
理論原価率が全店・全期間で約 2.7pt 低く出ていた。

  分子: 理論原価（fw_sheet ＝ 店長会シート・税抜）
  分母: 売上（SOURCE_PRIORITY で fw_uriage_suii ＝ 税込に統一済み）

原価率は低いほど良い指標なので、**全店が実力より優秀に見える方向**にずれる。
修正前は2026年だけが誤り、修正後は全期間が誤りになっていた。

対処は「どちらの税基準か」を当てにいくことではなく、**同じ表の中で割ること**。
理論原価は店長会シートの1枚から来るので、同じシートの売上で割れば、その
シートがどちらの基準でも比率は正しい。`analytics.SAME_SOURCE_RATIOS` に
`cost_rate: ("fw_sheet",)` を宣言し、`AggregateQuery.sources` で絞る。
売上そのものの表示は従来どおり税込のまま（テストで両方固定した）。

**新しい比率指標を足すときは、分子と分母が同じ口から来るかを必ず確かめること。**
違う口から来るなら `SAME_SOURCE_RATIOS` に載せる。

### まだ確かめていない比率

- **予算達成率**（実績 ÷ FW月別予算）。予算が税抜なら全店が約10%高く出る。
  FWの予算画面がどちらの基準かを確認すること。
- **客単価**（売上 ÷ 客数）。税込に統一した時点で定義が変わった。過去に配った
  税抜ベースの客単価とは接続しない。

## 部門が取れる月は店によって違う（1111 / 1151 / 1168）

FWのABCで商品に部門（分類）が紐付いているかは、店ごと・月ごとに違う。

  - 全期間だめ … 1069 ひよこ飯店 / 1137（`abc_dept: false`）
  - 途中から取れる … **1111 ちゃーちゃん・1151 NagaGutsu・1168 GOLD京都ポルタ**
    24ヶ月のうち部門があるのは 2026-07 と 2026-08 だけ。2026-07 は月の途中から
    紐付いたので部分的（1168 は売上の 2.9%、1111 は 3.7%）で、2026-08 から正常。

この3店に `abc_dept: false` を付けてはいけない。2026-08 以降の部門が
永久に取れなくなる。

2026-07 を何度入れ直しても同じ値になる（実際に確かめた）。取込の失敗ではないので、
`data-audit` の ③ は「部門を取り始めた月」を除外して、参考として別枠に出す。

## 同じ指標を二つの口が書くと、流した順で画面の数字が変わる（2026-09 に発覚）

月次の `sales` は二つの取り込み口が書く:

  - `fw_sheet`（店長会シート・`ingest.yml` で毎日）… **税抜**
  - `fw_uriage_suii`（月別日別売上推移・手動バックフィル）… **税込**

`replace_actuals` の入れ替え範囲は `(source, grain, date)` なので、両方の行は
共存できる。そして重複排除の並び順が `kind` → `ingested_at DESC` だけで
`source` を見ていなかったため、**後から入った方が勝つ**状態だった。

実際に起きていたこと:

  - 2024-09〜2025-12 は `fw_uriage_suii` だけ（税込）
  - 2026-01 から `fw_sheet` が入り始め、そちらが採用された（税抜）
  - 結果、**2026年の前年同月比が軒並み約9%低く出ていた**
    （1006 2026-01 は 88.4% と表示。正しくは 97.2%）
  - `部門合計 ÷ 月次売上` が2026年だけ109%で横ばい（2025年は99.8%）

見つけ方は `fw.yml --mode source-audit`。月ごとに「どの source が何店ぶん
書いているか」を並べ、切り替わった月と、同じ (店,月) を複数 source が持って
値がずれている組を出す。切替か食い違いがあれば非0で終了する。

対処は `db/warehouse.py` の `SOURCE_PRIORITY`。取り込み口に順位を付けて、
全期間を税込（`fw_uriage_suii`）に揃えた。ABC（部門・商品）も税込なので、
これで上の検算も合う。

**新しい取り込み口を足すときは、必ず `SOURCE_PRIORITY` に載せること。**
載せ忘れると既定値50で最下位になり、既存の口が勝ち続ける（黙って無視される）。

## FWツール早見（GitHub Actions: fw.yml を workflow_dispatch）
- `abc-store-ingest` … 1店の商品ABC＋部門内訳をNeonへ取込（本番収集の主力）
- `abc-coverage` … 全店の取得状況をDB照会で一覧（FW不要）
- `abc-store-probe` … 1店・任意期間の商品ABC（全商品/部門/グループ/メニュー、ランチ部門も）
- `abc-totals-probe` … 1店・複数期間のグループ合計（フード/ドリンク/飲み放題→品数・有料単価）
- `hourly-store-probe` … 1店・複数期間の時間帯別（客数・売上・客単価）
- `menu-hourly-probe` … 1店・複数期間の時間帯別メニュー出数（時間帯×商品の出数＝深夜の品数）
- `lunch-analyze` … 新ランチの開始日検出＋期間比較
