## いま繋がっているもの

### FW共有シート（月次・9指標）

既存パイプライン `infomart_automation`（`amami-cell/-`）の `foodist_journal.py` が、
FW（Foodist Journal / HASSIN, `pros-asp.net/corp/hassin`）の
**損益管理 → 実績管理業務 → 店長会資料DL** から Excel を1本ダウンロードし、
解析結果を Google スプレッドシート `18Fq_mpEweHOFTlF4ntmwJzDsJNSt-DOq7wQYy8E0iLc` に
書き込んでいる。

| 項目 | 実態 |
|---|---|
| 実行頻度 | 月2回（毎月 3〜5日 と 16〜20日 の 09:00 JST、GitHub Actions の cron） |
| 確定区分 | 1〜17日の実行 = 「中間」、18日以降 = 「確定」 |
| Excel の形 | **全店で1ファイル**、1シート＝1店舗（エリア「イニシエート」を全選択してDL） |
| Excel の残り方 | Actions ランナーの `./downloads` に落ちるだけで、**ジョブ終了後に消える** |
| シートの形 | 指標ごとにタブ。各行 = A:年月 / B:店舗名 / C:金額 / D:種別 / E:取込日時 |

このシステムは**このシートを読むだけ**。Excel を取り直したり、
既存パイプラインに手を入れたりはしない。

`確定` は同じ年月の `中間` を上書きする。取り込み後の集計でも、
同一 (店舗×年月×指標) に両方あれば `確定` を採る。

当初の構想では、以下が既存資産から取れる前提だった。**実際には取れていない**。

| 欲しいもの | 現状 | 影響 |
|---|---|---|

| 客単価 `avg_check` | 取得していない | `avg_check` 型施策が出せない |
| ABC分析（商品×売上） | 取得していない | `share` 型施策の分子が作れない |

いずれも FW の別画面にあると思われるが、既存コードはそこへ遷移していない
（`foodist_journal.py` のナビゲーションは店長会資料DL 一本）。

### 埋めるときにやること

1. FW のどのメニューに時間帯別売上／ABC分析があるかを特定する
2. `foodist_journal.py` と同じ Playwright パターンで新しいスクレイパーを書く
   （ログイン情報は既存の `FOODIST_JOURNAL_USER_ID` / `FOODIST_JOURNAL_PASSWORD`）
3. `hansoku/ingest/` に取り込みモジュールを1つ足す

**スキーマ変更は不要**。`f_actuals` は最初から次を持たせてある:

- `grain` … `'hour'` を入れれば時間粒度として区別される
- `hour` … 0〜23
- `product_name` / `product_category` … ABC分析の商品識別（カテゴリ優先、商品名フォールバック）

集計側も `grain` と `hour` での絞り込みに対応済みで、テストも通してある
（`tests/test_aggregate.py::Test時間帯で集計できる`）。
実データが流し込まれた時点で、そのまま動く。

## 店舗マスタ

`config/stores.yaml`。**FW共有シートに実際に現れた店名を正**として作ってある。

- **24店舗**（当初想定は26店舗）
- `store_code` は **FW（Foodist Journal）の店舗コード**（例 `1015`, `1154`）
- 14ブランド。すさび湯が7店で最多
- 共営施設（ルクア・パナンテ・京都ポルタ）は `is_shared_facility: true`

### ⚠ FW とインフォマートは別のコード体系

これは実データを取り込んで初めて判明した。取り違えると別の店の数字が混ざる。

| 店舗 | FW | インフォマート |
|---|---|---|
| 熊の鳥焼 | 1154 | 922 |
| ちゃーちゃん | 1111 | 923 |
| 料理と酒 たいだい | 1137 | 924 |
| 曲ル角ニハ泡喰ライ | 1115 | 925 |
| ひよこ飯店 | 1069 | 926 |
| んだんだ | 2004 | 936 |
| 大衆寿司酒場すさび湯 | 1006 | 956 |
| CRAFTMAN UMAMI | 1131 | 960 |
| ARATA | 1097 | 973 |
| 味のたぬきや | 1162 | 974 |

残り13店は偶然コードが一致している（1015・1151・1160・1163・1168・1169・1712・1713・1728・1729・1739・1742・1743）ため、
一部だけ見て「同じ体系だ」と判断すると事故になる。

実績の主データ源は FW なので `store_code` は FW 側を正とし、
インフォマートのコードは `infomart_code` 列に持たせてある。
原価・仕入をインフォマートから取り込むときは `by_infomart_code()` で突き合わせること。

なお `ぎふや 福岡天神店`（FW=1766）はインフォマート側に登録が無い新店。

### 店名からの店舗解決

FW共有シートの店名は `0001015_すさび湯 歌舞伎町` のように**先頭にゼロ埋めコードを含む**。
店名の表記は変わりうるがコードは変わらないため、取り込みではコードを最優先で使い、
コードが無い形式のときだけ店名の正規化突き合わせにフォールバックする。

新店は 1ブロック足すだけで、集約ループにも `scope=group` の展開先にも入る。

## 損益（原価率）の取込状況 — 監査でわかったこと

原価率＝(フード理論原価＋ドリンク理論原価) ÷ (F売上＋D売上)。分子・分母のどちらかが
欠ける店・月は原価率が出せず、画面では「―」になる。

**棚卸しの回し方**（読み取りのみ）:

- 手元/CI: `python scripts/audit_cost.py`（環境変数 `AUDIT_FROM` / `AUDIT_TO` = `YYYY-MM`、既定は直近12ヶ月）
- 画面から: 「実績を集計して見る」ワークフロー（`query.yml`）の `audit_cost` を on にして実行
  （作業ブランチ指定で今すぐ動く。既定ブランチにマージ後は `audit-cost.yml` 単体でも可）
- 未取込/一部/全月そろい に分類し、未取込店は「理論原価が無いのか F/D売上が無いのか」も出す

**2025-09〜2026-08 で回した結果（実測）**:

| 区分 | 店数 | 中身 |
|---|---|---|
| ✗ 完全未取込（0ヶ月） | 2 | 1743 すさび湯新宿東口、1766 ぎふや福岡天神（理論原価もF/D売上も無し） |
| △ 一部のみ | 21 | **全店が 2025-09〜2025-12 の4ヶ月を欠落**。加えて店固有の穴あり |
| ✓ 全月そろい | 0 | 全店が2025年秋冬を欠くため |

**要点：これは「特定店の問題」ではなく「期間の問題」**。共有シートの損益（店長会資料DL）が
概ね 2026-01 以降しか流れていない。店固有の追加欠落は 1151 NagaGutsu（2/12・2026-07,08のみ）、
1111 ちゃーちゃん・1168 GOLD京都ポルタ（4/12・2026-01〜04のみ）、1069・1137（2026-08欠け）、
2004（2026-06欠け）。

画面側の扱い: `export.py` が店ごとに `cost_status`（pos=新レジ未接続 / new=新店・反映待ち /
none=FW未反映 / partial=直近のみ）を出し、原価率が出ない店には「―」ではなく理由バッジを表示する。
直近に原価率が出ている店（＝2025年の歴史的欠落だけの店）にはバッジを出さない。

### 2025-09〜12 の損益バックフィル手順（上流の運用）

このシステムはシートを読むだけなので、欠落4ヶ月を埋めるには**上流でその期間を共有シートに
出す**必要がある（コード変更は不要）:

1. `infomart_automation` の `foodist_journal.py` で、店長会資料DL を 2025-09〜2025-12 分について実行し、
   共有シート（`18Fq_...`）に該当年月の行を書き込む
2. 書き込み後、`ingest.yml`（毎日 10:30 JST の夜間 or 手動 dispatch）が該当行を冪等に取り込む
3. `python scripts/audit_cost.py` で 2025-09〜12 が「取込済」に変わったことを確認

## これから: 新レジ（新Uレジ）／ダイニー POS の取込（task#48）

FW共有シート経路に乗らない POS を使う店の実績・損益を `f_actuals` に入れる配管。

**対象店（現状）**: `config/stores.yaml` の `pos` で判別。

| pos | 店数 | 店 |
|---|---|---|
| `fw` | 22 | FW共有シート経由（既存） |
| `uleji`（新Uレジ） | 1 | 1766 ぎふや福岡天神 |
| `dyny`（ダイニー） | 0 | まだ無し |

**設計方針**（`fw_sheet.py` と同じ骨格で、独立モジュールを1つ足す）:

1. `hansoku/ingest/pos_uleji.py`（必要なら `pos_dyny.py`）を新設。
   入力（新Uレジ/ダイニーの出力：CSV/Excel/API のいずれか）を読む Reader。
2. 行を正規化 → `StoreMaster` で店解決（`pos != "fw"` の店だけを対象に）→ `ActualRow` を組み立てる。
   月次は `grain='month'`、時間帯が取れれば `grain='hour'`、ABCが取れれば `product_*` を付ける。
3. `warehouse.replace_actuals(rows, scope_stores=True, scope_metrics=True)` で冪等投入
   （他店・他指標を巻き込まない）。`source='pos_uleji'` 等で口を分ける。
4. `ingest.yml` にステップを足す（既存の FW/インフォマートと並べる）。

**スキーマ変更は不要**（`f_actuals` は grain/hour/product_* を最初から持つ）。原価率も
FW と同じ指標名（`food_theory_cost` / `drink_theory_cost` / `food_sales` / `drink_sales`）で
入れれば、既存の `ratio("cost_rate")` と画面がそのまま動く。

**着手に必要なもの（未確定）**: 新Uレジ/ダイニーの**出力サンプル1本**（列の並び・単位・税込/税抜・
年月や時間帯の持ち方）。これが分かれば Reader と正規化を実装できる。それまでは 1766 は
画面上「新レジ未接続」バッジのままとなる。
